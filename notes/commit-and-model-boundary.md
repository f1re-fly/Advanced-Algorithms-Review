# 提交问题与模型边界

## 为什么从commit开始

FLP 把 transaction commit 作为共识问题的典型来源：参与同一事务的 data managers 必须一致选择安装结果或丢弃结果，否则数据库可能不一致。这个动机很重要，但主定理并不依赖某个具体提交协议的细节，也不是专门证明 two-phase commit 或 three-phase commit 的某个步骤失败。

论文随后把问题抽象成：每个进程有一个 0/1 输入，已经决定的进程必须选择同一个值，并且 0 和 1 都要可能成为某些可达执行中的决定值。

FLP 为了让不可能性结果更有覆盖面，给协议保留了很宽的能力边界。进程可以有无界内部存储；一步内可以向有限多个进程发送消息；论文甚至允许一种 atomic broadcast 能力。消息系统可靠：消息不会损坏、重复或丢失；只要接收方无限多次尝试接收，发给它的消息最终会到达。

真正被拿掉的是时间信息和故障检测。进程速度没有相对上界，消息延迟可以任意长，系统没有同步时钟，也不假设能判断某个进程已经停止。因此，调度器不能作弊丢消息，却可以把“慢”和“死”保持为不可区分。

这个边界解释了为什么主稿里不应把结论写成“网络不可靠导致共识不可能”。FLP 的关键不是丢包，而是在可靠但完全异步的消息系统中，任何有限观察都可能只是更长延迟的前缀。

## commit方向与后续路线

原论文提到当时的异步 commit 协议都有一个 vulnerability window：在某个执行区间内，单个进程的延迟或不可达会让整体无限等待。FLP 证明把这个经验判断抽象成共识层面的不可能性：只要还要求确定性协议在所有 admissible runs 中终止，窗口无法完全消除。

这也说明后续工作为什么通常改变模型而不是反驳证明：

- bounded waiting 或 partial synchrony 给终止性增加时间结构；
- randomized consensus 改变确定性进展要求；
- failure detectors 增加关于进程失败的外部提示。
